06. A MAST-U equilibrium, and IMAS earns its keep

2026-09-30 · milestone M1

The decision

M1 asks us to wrap FreeGSNKE, the free-boundary equilibrium code. A free-boundary solver needs a machine description: where the magnetic field coils sit, what conducting structures surround the plasma, and where the walls are. We had assumed this meant assembling an ITER coil set from published geometry, and asked the owner to approve a data source (OQ-8).

Checking the FreeGSNKE repository first turned out to be worth the five minutes. It already ships machine descriptions for MAST-U (“MAST-U-like”, credited to UKAEA), ITER (from the public FUSE.jl project) and SPARC, all under the same LGPL licence as the code itself. Nothing had to be built by hand. The owner chose MAST-U, which is also the machine FreeGSNKE’s own examples and tests exercise most.

One boundary worth stating plainly: this is the MAST-U machine geometry, which is redistributable and therefore Tier A. MAST-U experimental shot data, read through pyuda, is a separate thing: Tier B, needs UKAEA access, and can never be a runtime dependency. This iteration touches only the geometry. The transport benchmark stays ITER hybrid, because no published TORAX MAST-U scenario exists and QLKNN, the neural transport model, is outside its training domain on a spherical tokamak.

Getting it to run at all

The M0 notes said FreeGSNKE “imports and works”. It imports, but nothing else: its numerical core, freegs4e, was never installed, so every submodule failed. Installing that was the easy part.

The harder part was a genuine dependency conflict. The newer FreeGSNKE (3.1.1) is the version we want, because it can write its equilibrium out in the IMAS standard format. But it declares that it needs imas-python 2.3 or newer, while TORAX pins that library to exactly 2.1.0. No package manager can satisfy both. Reading FreeGSNKE’s code showed it uses only two functions from that library, both present in 2.1.0. So it is installed without dependency resolution, and the tests exercise the IMAS writer to prove the combination actually works. The conflict is written down in the environment notes rather than left as a trap.

IMAS as the interface

This is the first time the M0 groundwork paid off in an unplanned way. FreeGSNKE can emit an IMAS equilibrium record, and tkit already knows how to read one. So the join between a free-boundary equilibrium code and our transport state is a standards-defined file, not a pile of bespoke attribute mappings.

It wasn’t quite free. FreeGSNKE’s output omits three quantities our side reads, so the wrapper fills them in:

quantity how
rho_tor — the radial coordinate we use from the toroidal magnetic flux the file does carry
dvolume_drho_tor — how volume grows with radius differentiate the volume profile
area — cross-section area of each flux surface from volume and the surface’s inner and outer radii (Pappus’ theorem)

The area reconstruction deserves a note. The obvious alternative, counting grid cells inside each flux surface, is unreliable for this plasma: it is diverted, so near the boundary the “inside” test also catches the private flux region below the X-point, which inflated the outermost area by 32%. The volume-based formula is accurate to about 2% at mid-radius, and area is carried for export only, never used in the transport solve. A test pins the related identity that actually matters: integrating dV/dρ recovers the enclosed volume to 2%.

A second subtlety is specific to spherical tokamaks. There are two different “minor radii”: the geometric half-width of the plasma (0.55 m here) and the radius derived from toroidal flux (0.83 m). On a conventional tokamak these are close; on MAST-U they are not, and conflating them would put a 50% error into every normalised gradient. The wrapper keeps them separate, and a test asserts the ordering.

It works

Building the machine and running a static forward solve for a diverted MAST-U plasma:

check result
solver convergence 4 × 10⁻¹⁰ in 26 iterations, ~43 s
plasma current 620 kA, matching the request to 10⁻³
magnetic axis R = 0.99 m, Z = −0.05 m (MAST-U-like)
IMAS record passes the data dictionary’s own validation
conversion to tkit q, V′, ⟨|∇ρ|²⟩, volume all positive and resampled onto our uniform grid to 10⁻¹⁰

The machine files are fetched on demand (python -m tkit.cli machine MAST-U) from a pinned upstream commit, and their SHA-256 hashes go into a provenance file, so a run can always be traced to the exact geometry it used. They are pickle files, which execute code when loaded, so the wrapper documents that they must come from the upstream repository and nowhere else.

Next

The equilibrium is currently a standalone solve. The useful next step is to feed it into the transport loop: take the geometry FreeGSNKE produces and let TORAX evolve profiles on it, which is what “integrated modelling” means in practice. That needs a transport model valid for a spherical tokamak, which is exactly the gap M2 and M3 are meant to fill.
